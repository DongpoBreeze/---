# User-configured AI

Date: 2026-10-21. Users configure their own URL, key, model and reasoning effort in the App. Saved configuration survives Web refresh and reopening the same browser/origin, with `http://localhost:8081/` as the fixed development entry. The phone connects directly to the selected provider. Specifications and dated validation records are indexed in [the documentation guide](README.md).

## Behavior and boundaries

- The Android APK contains no developer gateway address, access token or provider credential. The user's phone connects directly to their chosen HTTPS service.
- Settings contain a base URL, API key, protocol (Responses or Chat Completions), model and optional reasoning effort. Native configuration remains in SecureStore independently of health records. Web configuration is committed to a separate IndexedDB database (`health-compass-ai-settings-v1`), outside the health snapshot database; health backups never contain either credential store. A successful Web save waits for the write transaction to commit with strict durability. There is no silent fallback to session memory when storage fails.
- Web settings and health profiles are scoped to the browser profile and origin (scheme, hostname and port). Refresh and reopening the same address restore saved values; `localhost`, `127.0.0.1`, another port or another browser have separate stores. Clearing browser site data removes its local settings. This change does not move credentials across origins or recover configuration already lost by the previous memory-only Web implementation.
- Height, weight, goal and optional calorie target remain in the existing atomic health snapshot. Successful saves are acknowledged after persistence, including on Web. Initial AI read failures do not prevent offline health use: the page shows a separate error and the settings row offers a retry without presenting an empty replacement form or clearing stored values. A separate explicit reconfiguration action can replace or delete unreadable AI settings while keeping the health profile and records. Failed writes keep the saved configuration and the user's pending form input; errors contain no credentials. Analysis during initial loading reports that settings are being read instead of claiming they are absent.
- Fetch `GET /models` with the entered credential. Let users choose returned models and advertised reasoning efforts. Optionally retrieve the selected model's metadata. There is no standard reasoning-capability discovery endpoint: absent metadata does not generate a guessed list or trigger paid probing. Users can choose the service default or explicitly enter a custom effort even when metadata is absent.
- “测试连接” sends one short generation request using the unsaved URL, Key, protocol, selected model and current effort. A successful status means the service returned a complete, non-empty response; it does not save settings or create a health record. The request times out after 20 seconds, can be cancelled, and may incur a small provider charge.
- The custom field accepts a provider-defined effort token within the existing limit of 64 ASCII letters, digits, dots, underscores or hyphens. Invalid input cannot be saved. The chosen token is sent unchanged as Responses `reasoning.effort` or Chat Completions `reasoning_effort`; it is not mapped to another level or silently reduced. Choosing the service default omits the parameter. A user-entered token does not assert that the provider supports it; provider rejections remain normal request errors.
- Saved non-default efforts remain editable after reopening settings. A non-empty stored token can be restored as custom without requiring fresh capability metadata. Re-fetching metadata for the same model must not silently discard a custom value.
- Changing URL, key, protocol or model invalidates dependent discovery/selection state. Stale discovery responses must not overwrite current input. Saving and deleting settings abort active analysis; old results must not become current.
- Meal recognition uses the minimal frontend JSON protocol with strictly validated AI per-100 g references. Intake is calculated locally from confirmed reference estimates or user-entered quantities, with separate provenance and explicit clearing; the model's original quantity stays empty and estimates are not photo measurements. USDA references remain available for legacy records. The key is never sent to the old developer gateway, health backup, logs, prompt or model-selection metadata. Details: [nutrition implementation](nutrition-implementation.md).
- HTTPS is required for every user-entered service address, including loopback. No LAN listener, public tunnel or firewall changes are part of this build.
- Existing offline health features stay free. External AI usage is billed according to the user's selected provider; the development gateway's budget ledger does not govern direct calls.

## Acceptance

1. Start unconfigured, edit connection, request models, select a model and advertised/custom/default effort, test connectivity, save, refresh/reopen and delete settings. Restore every saved field in both protocols and restore the health profile. Deletion persists across reopening while health records remain.
2. Verify custom effort with and without metadata, invalid input, restoring a saved value, metadata refresh, connection changes, cancellation and late results. Connection tests verify the selected model and protocol, classify provider errors safely, and never persist credentials or results. No automatic inference retry or hidden real-provider calls.
3. Mock Responses and Chat Completions requests contain the selected model/effort and preserve nutrition/summary validation.
4. Typecheck, focused unit tests and mobile/desktop UI flows pass; original health backup roundtrip still passes and excludes credentials.
5. Build a standalone signed Android test APK with current code, inspect package/native SecureStore inclusion and verify no bundled developer credentials. Real-device installation and provider-specific compatibility are reported separately.

The 2026-10-21 persistence verification does not itself establish a new APK build or that an inaccessible user's previously entered values have been saved on their behalf. See [Android testing](android-testing.md) for the latest built APK and its separate source and device-verification scope. Personal browser settings are never copied into a release package.

Official model-list reference: https://developers.openai.com/api/reference/resources/models/methods/list (read on 2026-10-11; basic model metadata has no standard reasoning-effort list).
