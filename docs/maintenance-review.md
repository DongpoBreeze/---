## 整理时确认的问题（已修复）

以下三项先由隔离的生产组件或 Hook 重放确认，之后已按各自回归验收完成修复。保留原现象与原因，方便追溯。

### P1：饮食草稿未完整保存已确认分析（已修复）

- 位置：[餐食表单](../src/ui/meal-form.tsx)第 83 行的 `useFormDraft`，以及其后的分析状态与 Ref。
- 现象：识别完成、填入 250 g 并确认后，关闭主表单再重开，名称和四项总量仍在，逐菜数量、组件与原模型历史无法从草稿恢复；随后保存可能只留下 `local/manual-nutrition`。
- 原因：主表单字段进入持久草稿，识别结果、逐菜数量和分析历史仅保存在组件状态与 Ref。
- 修复：版本化 `analysisDraft` 保存已确认结果、数量/清空状态、人工营养、模型历史与待确认编辑；旧扁平草稿继续读取。坏草稿和过期记录基线不覆盖旧数据。新餐食未确认就直接保存时，原始识别仍是当前版本，估算量只进入待核对历史，不进入摄入汇总；仅有历史快照时不生成空白手动营养版本。
- 验收：生产表单/Hook、JSON 存储和 ZIP 往返用例通过；手机与桌面覆盖确认、关闭、刷新、继续修改、保存及恢复。

### P2：已保存餐食重新分析会让当前摄入量退出汇总（已修复）

- 位置：[App](../App.tsx)第 588 行附近追加分析版本的逻辑，以及[领域计算](../src/domain.ts)第 59 行的 `mealCalories`。
- 现象：原餐食已有 250 g 和对应热量，重新分析同一道菜后，新的原始结果没有数量，被当作最新分析；当前热量变成未知，退出当天汇总，原量仍留在旧历史中。
- 修复：重新分析先进入现有餐食表单流程；用户确认并保存前不写入正式记录。菜名、做法唯一匹配才带回数量；改名、做法差异、重复及身份含糊的菜品保持空量待核。
- 验收：覆盖重排、改名、改做法、重复、身份不明、失败、取消、关闭及迟到响应；确认前旧记录/摘要不变，确认保存后才切换到新有效摄入。

### P2：训练草稿无法持久保存视频删除动作（已修复）

- 位置：[训练表单](../src/ui/training-form.tsx)第 486 行，以及[通用草稿恢复](../src/ui/useFormDraft.ts)第 188 行附近。
- 现象：编辑已有训练、移除视频、关闭后重开，原视频再次出现。
- 原因：删除用 `undefined` 表示，JSON 序列化省略该字段；草稿恢复时又沿用原记录的视频。
- 修复：训练草稿用空字符串保存明确删除意图，正式提交时转为空 URI；旧草稿缺字段仍继承原附件。
- 验收：力量、有氧模式均覆盖关闭重开、导出恢复、替换、保存和旧草稿兼容。

## 后续优化顺序

| 优先级 | 建议 | 依据及验收方向 |
|---|---|---|
| P2 | 更新移动端构建并完成设备验收 | 现有 APK 落后当前工作树。后续构建时验证升级、餐食分析草稿恢复、重分析、训练附件删除、相机/相册、多照片、主题和 AI 设置；arm64 实体手机与 iOS 分别记录结果 |
| P3 | 减少文字自动保存时的媒体工作 | `useFormDraft.ts:214` 每 350 ms 停顿提交；`storage.ts:263` 的媒体清理会遍历引用、解码 Data URL 并重新求摘要。建议持久化短媒体引用，复用摘要，只在引用集合变化时清理。先用较多照片和视频的本地数据测量，再优化；本轮没有性能基准 |
| P3 | 收敛餐食状态与版本职责 | 将识别草稿、已确认结果、原始历史和有效摄入的转换放在可单测的统一接口中，供新建、编辑和重新分析共用。避免多处组件状态分别承担同一版本的生效判断 |
| P3 | 避免构建产物再次重复累积 | `android-build.ps1` 会复制别名和 previous 包。后续可保留时间戳 APK，加小型最新版本索引；APK 检查优先保留 JSON 报告，bundle/转储按需提取 |

代码审查未发现可以直接删除的 npm 依赖。原生/网页平台模块、旧备份兼容、USDA 历史计算和诊断脚本继续保留；仅凭未跟踪状态、文件日期或文件名不能判定其无用。
